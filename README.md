# 阴阳师自动化助手

Windows 桌面程序：自动检测运行中的阴阳师客户端、支持多实例、参数配置、手动启停、按画面自动点按钮。
打包为独立 exe，**终端用户无需安装 Python 或 Node**。

---

打包好的程序放在本仓库的 **Releases** 页
（exe 有 204 MB，超过 GitHub 单文件 100 MB 限制，所以只能作为 Release 附件发布）。

## ⚠️ 风险告知（先读）

- 阴阳师用户协议**禁止**第三方自动化。后果按严重程度：警告 → 禁言 → 回档 → **永久封号**。判定权在运营侧。
- 当前实现的截图部分（GDI BitBlt）是**只读**的，不接触游戏进程内存，风险较低。
- 点击默认走**窗口消息投递**（不动物理光标），被拒时回退 `SendInput`。
  两者都属于软件注入，是最容易被反作弊识别的环节。
- **不要用主账号测试。**

### 「鼠标动了但没点击」的真相

实测确认 **SendInput 点击在这游戏上是有效的**：
- 脚本直接点屏幕坐标 → 游戏界面确实发生跳转
- 规则命中「自动」按钮后连续 4 次点击，分数 0.996–0.999

之前点不动的真正原因是 **Windows 权限隔离（UIPI）**：游戏以管理员运行（High），
而助手是普通权限（Medium），系统会丢弃所有按键输入 —— 光标能动、点击不生效。
现在 exe 已设为 `requireAdministrator`，详见下面「必须以管理员身份运行」一节。

```
[ OK ] 副本「御魂」  -> 素材齐全 9/9
```

> **历史坑（已修）**：早期版本素材存在 `resources/`、规则却从开发目录读，
> 导致「刚标定完却报素材缺失」。现在配置目录是唯一来源，
> `test-paths.js`（36 项）锁死「保存位置 == 加载位置」这个不变量。

### 素材名写法很宽松

`btn_x`、`btn_x.png`、`btn_x.PNG` 都等价，存下来统一是 `btn_x.png`。
手工编辑副本 json 时写 `"template": "btn_x"`（漏扩展名）或 `"btn_x.png.png"`（多一层）
也能自动纠正 —— 程序会把它修成磁盘上真实存在的文件名，并在日志里说明。

## ⚠️ 必须以管理员身份运行

**这是「鼠标动了但游戏没反应」的真正原因。**

实测对比：

| 进程 | 完整性级别 |
|---|---|
| 游戏 `onmyoji.exe` | **High（管理员运行）** |
| 助手（普通启动） | Medium |

Windows 的 **UIPI**（用户界面特权隔离）规定：低权限进程不能给高权限窗口发输入。
实测直接给游戏窗口发消息，三种都返回 `ERROR_ACCESS_DENIED (5)`：

```
WM_MOUSEMOVE    PostMessage=false  GetLastError=5  ERROR_ACCESS_DENIED
WM_LBUTTONDOWN  PostMessage=false  GetLastError=5  ERROR_ACCESS_DENIED
WM_LBUTTONUP    PostMessage=false  GetLastError=5  ERROR_ACCESS_DENIED
```

`SendInput` 的表现更迷惑：**光标会动**（那是系统级操作），但按键事件被丢弃 ——
所以看起来「鼠标移过去了，就是点不下去」。

**解法**：exe 的清单已经设成 `requireAdministrator`，双击会弹 UAC，**点是**即可。
自检里也能看到当前权限：

```
[6.5] 权限
[ OK ] 运行权限 -> 管理员（可以给管理员权限的游戏窗口发送点击）
```

## 点击方式：消息投递（不抢鼠标）

默认用 `PostMessage` 把鼠标消息投给游戏窗口，**物理光标完全不动**，
你可以同时用鼠标做别的事。实测自己的窗口：光标位移 0px，目标窗口收到了 down/up。

如果消息被拒（权限不足），会**自动回退**到 `SendInput`（会移动光标），并在日志里说明。
想强制用 SendInput，可在参数里设 `inputMode: 'sendinput'`。

**为什么要随机**：固定的点击位置 + 固定的毫秒级间隔，是最典型的脚本特征。
- 点击抖动 35%：在按钮区域内以中心为准的 35% 范围内随机取点
- 间隔 0.6–1.5 秒：每轮重新取值，实测点击间隔会落在 300–600ms 各种不同值上
- 触发概率 100% 之外的值：命中后有一定概率"这一轮先不动"，下轮再看

### 排查「鼠标动了但点不动」

面板底部有「**测试点击（鼠标当前位置）**」按钮：

1. 把鼠标移到游戏里任意安全位置
2. 点这个按钮
3. 看日志：
   - `点击测试成功：屏幕(x,y)，已发送 3/3 步` → 输入链路正常
   - `点击测试失败：...` → 输入被系统拦了，会给出已发了几步

点击的做法是**分三次**发：纯移动 → 纯按下 → 停顿 20-60ms → 纯抬起。
早期版本把 `MOUSEEVENTF_MOVE` 和按下/抬起合并在同一次 SendInput 里，
表现就是「鼠标移到位置了，但游戏没有任何点击反应」。

### 程序卡死 / 无响应

如果出现过「点开始后程序无响应被关掉」，那是主线程被长时间阻塞。
已知两个原因都已修掉（详见 [VERIFIED-FACTS.md](VERIFIED-FACTS.md) 第零之九节）：

1. **大模板掉进全分辨率匹配**：素材裁得越大反而越慢。修复后 9.7 倍提升（三模板一帧 3254ms → 336ms）
2. **PrintWindow 阻塞**：已把它排到最后，默认不启用

**素材尺寸建议**：单个素材控制在 **200×120 以内**，既快又不易误匹配。
参考（1718×1019 内容区）：134×62 → 75ms，228×126 → 135ms，370×171 → 174ms。

如果还遇到卡顿，日志里会出现 `主线程被阻塞 xxxxs` 的行，把它发出来即可定位。

## 配置体系：一套副本 = 一个 json + 几张 png

**这是本程序的核心扩展方式。** 加一种新副本不需要改代码、不需要重新打包 ——
放好文件、重启程序，它就会出现在「副本类型」下拉栏里。

### 目录结构（就在 exe 旁边）

```
<安装目录>/
├── OnmyojiAssistant.exe
└── config/                    ← 打包发给别人时一起带上
    ├── dungeons/              ← 一种副本 = 一个 json
    │   ├── soul.json          （御魂）
    │   ├── awaken.json        （觉醒材料）
    │   ├── evolve.json        （御灵）
    │   └── common.json        （通用副本）
    ├── assets/                ← 所有素材 png，多个副本可共用
    └── screen.json            ← 素材基准尺寸 + 自动缩放开关
        ├── win.png
        ├── challenge.png        (棕字，未选中状态)
├── challenge_1.png      (黑字，可用状态)
        └── ...
```

程序每次启动都会扫一遍 `config/dungeons/*.json` 来填充下拉栏，
所以**加完文件重启就能看到**。面板「开发者选项 → 打开数据目录」直接打开这个 `config` 文件夹。

### 加一套新副本：3 步

**第 1 步：准备素材**

从游戏画面裁出按钮/文字，存成 png 放进 `config/assets/`。

```powershell
cd F:\WorkSpace\onmyoji-bot\app
npm run probe        # 抓一张 probe_<hwnd>.png，用任意截图工具从里面裁
```

裁剪要求：
- 必须是**内容区**截图（实测内容区 1718×1019，不是整个窗口）
- 只框文字或图标，别带大片纯色背景
- **宽度建议 ≤ 200px**（越大越慢，见「程序卡死」一节）
- 文件名用英文/数字/下划线

**第 2 步：写一个 json**

在 `config/dungeons/` 下新建 `你的副本id.json`：

```json
{
  "id": "mydungeon",
  "name": "我的副本",
  "order": 50,
  "description": "探索 → 我的副本 → 挑战 → 准备",
  "rules": [
    {
      "state": "战斗胜利",
      "template": "win.png",
      "threshold": 0.85,
      "action": { "type": "tap" },
      "cooldownMs": 900,
      "isBattleEnd": true
    },
    {
      "state": "挑战",
      "template": "challenge_1.png",
      "threshold": 0.86,
      "action": { "type": "tap" },
      "cooldownMs": 1500
    },
    {
      "state": "挑战·棕字",
      "template": "challenge.png",
      "threshold": 0.86,
      "action": { "type": "tap" },
      "cooldownMs": 1500
    },
    {
      "state": "进入我的副本",
      "template": "mydungeon_entry.png",
      "threshold": 0.87,
      "action": { "type": "tap" },
      "cooldownMs": 1200
    }
  ]
}
```

**第 3 步：重启程序**

下拉栏里就会出现「我的副本」。如果素材没放全，名字后面会带 `⚠`，
下方提示会写「缺 N 张素材」，日志里也会明确说缺哪个文件 —— 缺素材的规则会被跳过，不会崩。

### json 字段说明

**副本级**

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 内部标识，只能字母数字下划线横线。改了会被当成新类型 |
| `name` | ✅ | 下拉栏里显示的名字 |
| `order` | | 排序，小的在前（默认 100） |
| `description` | | 下拉栏下方的说明文字 |
| `rules` | ✅ | 规则数组，**顺序即优先级** |

**规则级**

| 字段 | 必填 | 说明 |
|---|---|---|
| `state` | ✅ | 状态名，显示在日志里 |
| `template` | ✅ | `config/assets/` 下的 png 文件名 |
| `threshold` | | 0–1，默认 0.86。**误触发调高，漏检调低** |
| `region` | | 可选 `[x,y,w,h]`（内容区坐标），限定搜索范围，能显著降低误判 |
| `action` | | `tap`（默认）/ `none` / `stop` |
| `cooldownMs` | | 命中后多少毫秒内不再重复命中，默认 800 |
| `repeat` | | 在 `action` 里写，连点次数（1–5，默认 1）。「点击屏幕继续」用 `repeat: 2` |
| `isBattleEnd` | | true 表示这条命中代表一场战斗结束（统计场次） |
| `_任意名字` | | 以 `_` 开头的是注释，程序会忽略 |

**关于 `cooldownMs` 的用法**：像「八岐大蛇」这种**选中后依然在画面上**的列表项，
靠冷却时间让位给后面的「挑战」规则 —— 点一次后 1.2 秒内不再点它，
这段时间里匹配就会往下走到「挑战」。

### 同一个按钮有多种外观：写多条规则，别调阈值

实测踩过的例子：「挑战」按钮有两种外观 ——

| 素材 | 外观 | 含义 |
|---|---|---|
| `challenge_1.png` | **黑字** | 可用状态 |
| `challenge.png` | **棕字** | 未选中/不可用状态 |

两张图彼此的相似度只有 **0.64**（用零均值归一化互相关算的）。
这意味着：**不能靠降阈值让一张覆盖两种** —— 想让它匹配棕字，阈值就得降到 0.64，
那样画面上几乎所有浅色区域都会命中，变成乱点。

正确做法是**各写一条规则**，阈值都保持 0.86 左右：

```json
{
  "state": "挑战",
  "template": "challenge_1.png",
  "threshold": 0.86,
  "cooldownMs": 1500
},
{
  "state": "挑战·棕字",
  "template": "challenge.png",
  "threshold": 0.86,
  "cooldownMs": 1500
}
```

> 经验法则：两张素材如果彼此相似度 **< 0.85**，就当两个模板分开写。
> 想快速比较两张图的相似度，可以用 `npm run test:vision` 里同款的 NCC 工具，
> 或直接看它们并排的截图 —— 颜色/字形明显不同就该分开。

### 动作类型

| type | 行为 |
|---|---|
| `tap` | 点击命中位置（在按钮内随机取点） |
| `none` | 只记录不点击（如「战斗中」状态） |
| `stop` | **立即正常停止本次运行**，可带 `reason` 说明 |

`stop` 是「保命」动作，典型用法：体力不足、出现购买体力弹窗、需要人工处理。
**放在规则数组最前面**（优先级最高），能避免在异常界面里继续乱点。

```json
{
  "state": "体力不足_停止",
  "template": "text_no_stamina.png",
  "threshold": 0.9,
  "action": { "type": "stop", "reason": "体力不足，已停止" }
}
```

| 文件 | 用途 |

## ⚠️ 窗口大小变了怎么办（自动缩放）

**这是最容易误判成「素材坏了」的问题。**

模板匹配对平移不敏感，但对**缩放极其敏感**。合成实验实测（同一素材贴到画布上，只改画面缩放）：

| 画面缩放 | 用原始素材匹配 | 把素材按同比例缩放后 |
|---|---|---|
| 1.000 | **1.000** ✅ | 1.000 ✅ |
| 0.950 | 0.583–0.890 ❌ | **1.000** ✅ |
| 0.900 | 0.273–0.677 ❌ | **1.000** ✅ |
| 0.874 | 0.000–0.607 ❌ | **1.000** ✅ |
| 0.800 | 0.000–0.565 ❌ | **1.000** ✅ |

也就是说：**画面只要缩小 5%，素材就大面积失效；缩小 12%，几乎全灭。**
症状是「所有素材一起识别不到」，而不是某一个不灵 —— 这就说明是全局缩放问题，不是素材裁坏了。

程序会自动处理：启动时读 `config/screen.json`，

```json
{
  "referenceWidth": 1718,
  "referenceHeight": 1019,
  "autoScale": true
}
```

按 `当前内容区宽度 / referenceWidth` 算出缩放比，把所有素材缩放到当前尺寸再匹配。
日志里会明确写一行：

```
info: 锁定内容区 1511x896，与素材基准宽 1718 相差 -12.0%，已把素材按 0.880 倍缩放后匹配
```

**`referenceWidth` 怎么填**：素材采集时的**内容区宽度**（不是窗口宽度）。
看日志里「已锁定内容区 WxH」那行，或跑 `npm run probe`。

**所有素材必须在同一个窗口尺寸下裁。** 如果混着不同尺寸裁的，个别素材会失效 ——
这时用「素材诊断」能立刻看出是哪几个。

## 输入后端说明（ADB / Windows）

点击支持**两种后端**，程序自动选择：

| 后端 | 适用场景 | 隐蔽性 |
|---|---|---|
| **ADB** `input tap` | 游戏跑在**真正运行中的** MuMu / 雷电虚拟机里 | 较高（模拟器内部注入，不经桌面输入栈） |
| **Win32 SendInput** | 「阴阳师-MuMu模拟器专版」这类**独立 PC 客户端** | 较低（桌面软件注入） |

**自动选择**：先做 TCP 端口快测（约 78ms）→ 有存活端口才尝试 ADB → 否则用 SendInput。
两者都不可用时**只识别不点击**，绝不静默降级到风险更高的方式。

### ⚠️ 你的环境下 ADB 不可用（实测）

如果你装的是 **「阴阳师-MuMu模拟器专版」**（`C:\Program Files (x86)\Netease\OnmyojiLauncher`），
它把模拟器**打包进了 PC 客户端**，没有运行中的 Android 虚拟机：

```
MuMuManager.exe info -v all  →  is_android_started: false
adb connect 127.0.0.1:17997  →  offline
对 17997 发 ADB 握手           →  无响应（不是 ADB 守护进程）
其余候选端口                    →  全部拒绝连接
```

**结论：ADB 天然不可用**，程序会自动改用 **Windows SendInput**。

**想让 ADB 可用**：把游戏装进**真正运行中的 MuMu 多开实例**（MuMu 12 支持多开且默认开 ADB），
程序会自动检测并切到 ADB 后端，**不需要改代码**。

完整调查过程见 [VERIFIED-FACTS.md](VERIFIED-FACTS.md) 第零之二节。

## 技术架构要点

### 为什么用 koffi 而不是原生模块

调用 Win32 API 需要 FFI。`node-window-manager` 这类是 C++ 原生模块，安装时走 `node-gyp` 编译，
需要几个 GB 的 Visual Studio Build Tools。**koffi 自带全平台预编译二进制，`npm install` 即用，零编译依赖。**

### 为什么截图能用但有讲究

实测三种方式对 MuMu 里的阴阳师：

| 方式 | 结果 | 性能 |
|---|---|---|
| **BitBlt** | ✅ 可用 | **4.8ms/帧（约 208fps）** |
| PrintWindow | ❌ 返回 false | — |
| PrintWindow + PW_RENDERFULLCONTENT | ❌ 返回 false | — |

**内容区问题（关键）**：模拟器客户区 1704×960，但阴阳师只渲染左上角 **1141×665**，
其余是模拟器填充的黑边。直接整窗截图会导致黑边拉低匹配分数、坐标错位。

所以实现了**自动内容区探测**（`capture.detectContentBounds`），
之后所有匹配和点击都换算到 ROI 内部。

**坐标换算基准**：

```
屏幕坐标 = 窗口原点 + ROI偏移(roi.x, roi.y) + 内容区内坐标
```

`capture.grabContent()` 一次返回全部三项。

### 截图降级链（重要）

窗口 DC 能否拿到画面**不稳定**：同一台 MuMu，有时亮度 92（正常）、有时 0（全黑），
取决于模拟器的渲染状态。所以截图走**降级链**，全黑就自动换下一级：

| 顺序 | 方式 | 特点 |
|---|---|---|
| 1 | `bitblt`（窗口 DC） | 最快，不受遮挡；可能全黑 |
| 2 | `printwindow_full` / `printwindow` | 让窗口自己重绘；对部分窗口返回 false |
| 3 | `screen`（屏幕 DC） | 几乎总能拿到画面；**窗口被遮挡时会抓进遮挡物** |

`capture.grabContent()` 返回的 `method` 字段告诉你**实际**用了哪一级，
`warning` 字段在全部失败时给出原因。探针会逐级报告每种方式在该窗口上的可用性。

### 游戏窗口识别（踩过坑）

判定顺序**不能改**：

1. 进程名精确匹配 `onmyoji.exe` —— 最可靠
2. 进程名包含 `onmyoji`
3. 标题含关键字，且排除自身和其他 Electron 应用
4. 按面积取最大

必须过滤的干扰项：MuMu 会创建多个**标题完全相同**、坐标在 `(-48000,-48000)` 的隐藏辅助窗口。
另外其他应用窗口标题里可能碰巧含「阴阳师」（实测 DeepSeek Harness 自己的窗口就是）。

### 模板匹配的实现选择

| 方案 | 结论 |
|---|---|
| 逐像素差（SAD/SSD） | ❌ 整体亮度一变就失效 |
| **NCC + FFT** | ✅ **采用**。NCC 抗亮度变化，FFT 把 O(W·H·w·h) 降到 O(WH log WH) |
| opencv-wasm | 可行但依赖重（~10MB wasm），且加载慢 |

**由粗到精两级搜索**（关键的性能优化）：

1. 粗搜：帧和模板都降采样 1/4，用 FFT 做全图 NCC
2. 精修：对前 5 个候选，在原始分辨率上做局部 NCC

实测：1712×1016 全图单模板 **74ms/帧**。不降采样的话要 **1055ms**（慢 14 倍）。

**踩过的数学坑**：频域做相关必须用 `A·conj(B)`。如果既对模板做空间翻转、
又直接相乘，得到的是**卷积**，峰值错位且分数会溢出 1.0（实测出现过 1.5131）。

### 为什么点击用 ADB 而不是 SendInput

| 方案 | 隐蔽性 | 说明 |
|---|---|---|
| `SendInput` / `mouse_event` | 低 | 桌面软件注入，最易被反作弊识别 |
| **ADB `input tap`** | **中高** | **采用**。从模拟器内部注入，不经桌面输入栈 |
| Arduino HID | 高 | 真实 USB 输入，但需要额外硬件 |

ADB 不可用时程序会**明确告警并只识别不点击**，不会静默降级到 `SendInput` ——
避免在你不知情的情况下用上风险更高的方式。

## 怎么看运行日志

日志会明确告诉你「现在走到哪一步」，以及「没匹配上时在等什么」。

**正常推进时** —— 每次步骤变化打一条（同一按钮不会重复刷）：

```
info: 步骤: 进入探索（分数 0.941）
info: 点击 [进入探索] 屏幕坐标(3170,883) 分数 0.941
info: 步骤: 进入御魂（分数 0.905）
info: 点击 [进入御魂] 屏幕坐标(2894,712) 分数 0.905
info: 步骤: 选择八岐大蛇（分数 0.882）
info: 步骤: 挑战（分数 0.913）
info: 点击 [挑战] 屏幕坐标(3320,941) 分数 0.913
ok:   完成第 1 场 (战斗胜利)
```

**匹配不到任何画面时**（以前这里是完全静默的，看起来像卡死）：

```
info: 等待中: 当前画面没有匹配到任何规则（连续 5 帧 / 4.2s）
info: 正在等这些画面: 战斗胜利 / 通关奖励 / 通关结算 / 准备 / 挑战 … 等 10 项
info: 如果一直停在这里：战斗中/加载中属正常；若明显卡住，多半是素材和当前界面不一致
warn: 仍在等待（已 26s 无匹配）: 正在等 战斗胜利 / 通关奖励 / 通关结算 … 等 10 项
```

**怎么判断是「正常等待」还是「出问题了」**：

| 情况 | 判断 |
|---|---|
| 战斗中、加载中、翻页动画 | 正常，会自己恢复，日志接下来出现「步骤: …」 |
| 一直等，且 `正在等这些画面` 里明明有当前该出现的按钮 | **素材对不上** —— 截图看这个按钮现在长什么样，重裁一张，或按「同一按钮多种外观」加一条规则 |
| 一直等，且画面停在某个没见过的新界面 | 流程里缺这个界面的规则，加一条即可 |

> 「等待中」只在连续 5 帧（约 3–7 秒）没匹配时打一次，之后每 20 秒提醒一次，
> 所以正常流程不会刷屏。

## 排错

| 现象 | 原因 / 处理 |
|---|---|
| `Cannot read properties of undefined (reading 'whenReady')` | `ELECTRON_RUN_AS_NODE` 被设置，清除它 |
| `Unknown or invalid type name` | koffi 回调类型写法错，用 `ProtoName *` 内联，见 `VERIFIED-FACTS.md` 坑 3 |
| 窗口枚举返回 0 个 | 用了 `Number(hwnd)` 转指针对象，必须用 `koffi.address()`，见坑 5 |
| 坐标整体偏 1.5 倍 | DPI 感知声明太晚，必须在建窗/测量前，见坑 6 |
| 截图右侧下方大片黑 | 没做内容区探测，用 `capture.grabContent()` |
| 检测到错误的窗口 | 按进程名优先，见 `lib/gamedetect.js` |
| `npm error EALLOWSCRIPTS` | `allowScripts` 要写进 `package.json`，不能用命令行参数，见坑 2 |
| `electron.exe --version` 输出 `v24.x`（Node 版本） | `ELECTRON_RUN_AS_NODE` 被设置，Electron 退化成了纯 Node。**这是 DSH shell 注入的**，exe 双击运行不受影响。详见 [VERIFIED-FACTS.md](VERIFIED-FACTS.md) 第零节 |
| 打包后 `exe --self-check` 报 `bad option` | 打包产物不接受自定义 `--` 开关（Chromium 解析）。`--self-check` 只在开发态 `npm run selfcheck` 可用 |
| harness 里跑任何命令都报 `grantWrite(...)` 失败 | 沙箱写入限制，见下节 |

完整技术细节和实测数据见 **[VERIFIED-FACTS.md](VERIFIED-FACTS.md)**。

### 在 DSH harness 里构建时的沙箱问题

在 `workspace-write` 模式下，DSH 沙箱**读**工作区正常，但**写**会被拒（连建目录都不行）：

```
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(F:\WorkSpace)
```

已用官方 ACL 诊断脚本修过两层路径（`F:\WorkSpace` 和 `F:\WorkSpace\onmyoji-bot`，
`writeOwner` 均从 `false` 修到 `true` 且验证通过），**但写入仍被拒** ——
说明沙箱在文件权限之外还有自己的约束（ACL 里有 `LOW_LABEL` 完整性标签）。

**处理办法（二选一）**：

1. **把会话切到「完全权限」(full access)** —— 推荐，之后安装和编译全自动，无需逐条批准
2. 对需要写操作的单条命令单独批准：带 `sandbox_permissions: danger-full-access` 走一次审批
   （实测重新编译 exe 只需 **8.5 秒**）

详细诊断过程和证据见 [session-startup-record.md](session-startup-record.md) 第零节。
